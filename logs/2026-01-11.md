## Issue 3: CRITICAL - Duplicate Orders & Payment Not Working

### Root Causes Found
1. **Duplicate orders**: Webhook created one order, React Native app created another
2. **Payment never captured**: `capture_payment` edge function was never called
3. **Wrong wallet system**: Local `wallets` table was being credited, but UI showed Stripe balance
4. **Seller not paid**: Stripe authorization expired after 7 days without capture

### Data Evidence
Two orders for same purchase:
- Order 1 (webhook): `price_cents=81`, `stripe_payment_intent_id=null`, `payment_status="succeeded"`
- Order 2 (app): `price_cents=50`, `stripe_payment_intent_id="pi_..."`, `payment_status="requires_capture"`

### Fixes Applied

#### 1. Removed duplicate order creation from webhook (`stripe-webhook/index.ts`)
- `payment_intent.succeeded` no longer calls `createOrUpdateOrderFromPayment()`
- `charge.succeeded` no longer calls `createOrUpdateOrderFromPayment()`
- App handles order creation; webhook only updates payment status

#### 2. Added payment capture to order completion (`orderService.ts`)
- `confirmDelivery()` now calls `capture_payment` edge function for card payments
- `verifyServicePIN()` now calls `capture_payment` edge function for card payments
- This actually charges the buyer and sends money to seller's Stripe Connect

#### 3. Fixed wallet architecture
- Card payments: Money flows via Stripe destination charges (no local wallet)
- Wallet payments: Local `wallets` table used for in-app transfers only
- Renamed `releaseEscrowFunds` → `releaseWalletEscrow` (only for wallet payments)
- Added `cancelStripePayment()` for refunds

#### 4. Stripe as single source of truth (`walletService.ts`)
- `getWalletBalance()` queries Stripe Connect balance only
- Deprecated `getBalance()` with warning
- Removed phantom escrow tracking from local DB

### Architecture After Fix
| Payment Method | Buyer Pays | Seller Receives | Source of Truth |
|----------------|------------|-----------------|-----------------|
| Card | Stripe charges card | Stripe Connect balance | Stripe API |
| Wallet | Local wallet debited | Local wallet credited | Local DB |

## Phase 1: Transaction Architecture Security Fixes

### Issue #9 & #10: Missing Authorization on Payment Edge Functions

Both `capture_payment` and `cancel_payment` edge functions accepted any `payment_intent_id` without verifying the caller had permission. Any authenticated user could capture or cancel any payment.

### Fixes Applied

#### 1. `capture_payment/index.ts` - Added Authorization
- Parse Authorization header and validate JWT token
- Look up order by `stripe_payment_intent_id`
- Verify caller is either buyer or seller on the order
- Only proceed with capture if authorized

#### 2. `cancel_payment/index.ts` - Added Authorization  
- Same auth pattern as capture_payment
- Both buyer and seller can cancel (buyer before seller confirms, seller if can't fulfill)
- Prevents arbitrary users from voiding other users' authorizations

### Issue #7: Payment Captured Before PIN Verification

In `verifyServicePIN()`, the Stripe payment was captured BEFORE the PIN was verified. If PIN was wrong, buyer was still charged.

### Fix Applied

#### `orderService.ts` - Reordered PIN Verification
**Before (WRONG):**
```
1. captureStripePayment()  ← Charges buyer first!
2. verify_service_pin RPC  ← PIN check happens after
3. releaseWalletEscrow()
```

**After (CORRECT):**
```
1. verify_service_pin RPC  ← PIN verified FIRST (throws on failure)
2. captureStripePayment()  ← Only charges buyer if PIN correct
3. releaseWalletEscrow()
```

### Files Modified
- `supabase/functions/capture_payment/index.ts`
- `supabase/functions/cancel_payment/index.ts`
- `mobile/src/services/orderService.ts`

### Deployment Note
Edge functions must be redeployed to Supabase for changes to take effect.

## Phase 2: Wallet Escrow Protection Fixes

### Issue #4: Wallet Payments Have No Escrow Protection

Wallet payments immediately deducted funds from buyer and directly credited seller on completion. If order was cancelled, funds were already with seller.

### Issue #5: Wallet Release is Not Atomic (Race Condition)

`releaseWalletEscrow()` did two separate DB operations: read wallet, update wallet. Race conditions could cause double-spending.

### Fixes Applied

#### 1. Created SQL RPC Functions (`docs/sql/release_wallet_escrow.sql`)

Two atomic functions to prevent race conditions:

- **`release_wallet_escrow()`**: Atomically moves funds from buyer's escrow to seller's available
- **`refund_wallet_escrow()`**: Atomically moves funds from buyer's escrow back to buyer's available

Both use `SECURITY DEFINER` and check balances before updating.

#### 2. Updated `deductFromWallet()` 
**Before:** Deducted from `available_cents` only
**After:** Moves funds from `available_cents` → `escrow_cents`

Buyer's funds are now held in escrow until order completes or is cancelled.

#### 3. Updated `releaseWalletEscrow()`
**Before:** Two separate queries (read then update) - race condition risk
**After:** Single atomic RPC call `release_wallet_escrow()`

#### 4. Updated `refundBuyer()`
**Before:** Added funds directly to buyer's available balance
**After:** Uses atomic RPC `refund_wallet_escrow()` to move from escrow → available

#### 5. Updated Order Payment Status
**Before:** Wallet payments set `payment_status = 'succeeded'` immediately
**After:** Wallet payments set `payment_status = 'in_escrow'` (funds held until completion)

### Database Migration Required
Run `docs/sql/release_wallet_escrow.sql` in Supabase SQL Editor to create the RPC functions.

### Wallet Payment Flow After Fix
```
1. Buyer places order → funds move: available → escrow
2. Order completes → RPC atomically: buyer.escrow → seller.available
3. Order cancelled → RPC atomically: buyer.escrow → buyer.available
```

## Phase 2: Fix Order Creation Timing (Race Condition)

### Problem
Payment was authorized BEFORE order existed in the database. If order creation failed after payment, an orphaned PaymentIntent existed with no associated order.

### Solution: Order-First Flow
Create the order first with `payment_status: 'pending'`, then process payment, then update order.

### Changes Made

#### 1. `orderService.ts` - Added `deletePendingOrder()` function
- Cleans up orders with `payment_status: 'pending'` when payment fails or is cancelled
- Validates caller is the buyer
- Only allows deletion of orders in 'pending' status

#### 2. `orderService.ts` - Updated `createOrder()` 
- Now accepts optional `payment_status` field in OrderCreate
- Defaults to 'pending' for the order-first flow
- Order created before payment attempt

#### 3. `types/order.ts` - Updated `OrderCreate` interface
- Added optional `payment_status?: 'pending' | 'requires_capture'` field

#### 4. `ListingDetailScreen.tsx` - Rewrote `handleCardPayment()`

**Old Flow (Problem):**
```
1. configurePaymentSheet() → Creates PaymentIntent
2. presentPaymentSheet() → User pays
3. createOrder() → Creates order with payment_intent_id
↑ If step 3 fails, orphaned PaymentIntent exists!
```

**New Flow (Fixed):**
```
1. Calculate prices locally (seller + Stripe fee)
2. createOrder() with payment_status: 'pending' → Creates order first
3. configurePaymentSheetForOrder() → Creates PaymentIntent for order
4. presentPaymentSheet() → User pays
5a. Success: updateOrderPaymentStatus() → Updates to 'requires_capture'
5b. Cancel/Fail: deletePendingOrder() → Cleans up pending order
```

#### 5. `ListingDetailScreen.tsx` - Added imports
- Added `configurePaymentSheetForOrder` from stripeService
- Added `deletePendingOrder`, `updateOrderPaymentStatus` from orderService

### Benefits
1. No orphaned PaymentIntents - order exists before payment attempt
2. Clean rollback on failure - pending orders are deleted if payment fails
3. Full audit trail - order tracks the complete transaction lifecycle
4. Edge function already supported this flow via `order_id` parameter

## Phase 3: Fix verifyServicePIN Order Completion

### Problem
After PIN verification and payment capture, `verifyServicePIN()` returned the order without updating status to `completed`. Order remained in previous status despite payment being captured.

### Solution
Added order status update after payment capture in `verifyServicePIN()`.

### Changes Made

#### `orderService.ts` - Updated `verifyServicePIN()`

**Before:**
```typescript
if (order.stripe_payment_intent_id) {
  await captureStripePayment(order.stripe_payment_intent_id);
}
return getOrderDetails(orderId);  // ← Just returns order, status unchanged
```

**After:**
```typescript
if (order.stripe_payment_intent_id) {
  await captureStripePayment(order.stripe_payment_intent_id);
}

// STEP 3: Mark order as completed
const { data: updatedOrder, error: updateError } = await supabase
  .from('orders')
  .update({
    order_status: 'completed',
    payment_status: 'succeeded',
    completed_at: new Date().toISOString(),
    updated_at: new Date().toISOString(),
  })
  .eq('id', orderId)
  .select()
  .single();

if (updateError) throw updateError;
return normalizeOrder(updatedOrder);  // ← Returns updated order
```

### Service Order Flow After Fix
```
1. Buyer places order → order_status: 'placed'
2. Seller sees PIN from buyer
3. Seller verifies PIN via verifyServicePIN():
   a. PIN validated via RPC
   b. Payment captured from buyer's card
   c. Order marked: order_status='completed', payment_status='succeeded'
```

## Phase 4: Enable Seller Cancellation

### Problem
`cancelOrder()` in `orderService.ts` only allowed buyers to cancel orders. The server RLS policies already permitted both buyer and seller to cancel, but the client-side check was too restrictive.

### Solution
Updated `cancelOrder()` authorization to allow both buyer and seller to cancel orders in 'placed' status.

### Changes Made

#### `orderService.ts` - Updated `cancelOrder()` authorization

**Before:**
```typescript
if (currentUserId !== order.buyer_id) {
  throw new Error('Unauthorized: Only buyer can cancel order');
}
```

**After:**
```typescript
if (currentUserId !== order.buyer_id && currentUserId !== order.seller_id) {
  throw new Error('Unauthorized: Only buyer or seller can cancel order');
}
```

Updated function comment from "buyer only" to "buyer or seller".

### UI Already Supported This
The `OrderDetailScreen.tsx` already showed the cancel button for both buyer and seller when `order.status === 'placed'`:
```typescript
if (order.status === 'placed' && (isBuyer || isSeller)) {
  actions.push(<Button key="cancel" title="Cancel Order" ... />);
}
```

No UI changes were needed - only the service authorization check.
