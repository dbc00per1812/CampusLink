# 2026-01-14 - Service Payment Edge Function Fix

## Issue
Test user received "Edge Function returned a non-2xx status code" error when trying to pay for a service-based listing from the Order Details screen.

## Root Cause
The `create_payment_intent` edge function was not handling orders with null `seller_price_cents` and `buyer_price_cents` fields. When these fields are null:
1. Direct assignment: `sellerPriceCents = order.seller_price_cents;` results in `null`
2. Subsequent calculations like `Math.round((sellerPriceCents * 0.029) + 30)` return `NaN`
3. Stripe API rejects the PaymentIntent with invalid amount

## Fix Applied
Updated `/supabase/functions/create_payment_intent/index.ts`:

1. **Added fallback pricing calculation**: When `seller_price_cents` or `buyer_price_cents` is null, now calculates from `price_cents`:
   ```js
   if (order.seller_price_cents !== null && order.buyer_price_cents !== null) {
     sellerPriceCents = order.seller_price_cents;
     buyerPriceCents = order.buyer_price_cents;
   } else {
     sellerPriceCents = order.price_cents;
     const calculatedStripeFeeCents = Math.round((sellerPriceCents * 0.029) + 30);
     buyerPriceCents = sellerPriceCents + calculatedStripeFeeCents;
   }
   ```

2. **Added pricing validation**: Added check before Stripe call to catch any invalid pricing:
   ```js
   if (!sellerPriceCents || !buyerPriceCents || 
       isNaN(sellerPriceCents) || isNaN(buyerPriceCents) ||
       sellerPriceCents <= 0 || buyerPriceCents <= 0) {
     throw new Error(`Invalid pricing data...`);
   }
   ```

3. **Added `price_cents` to query**: Updated the order query to include `price_cents` for fallback calculation.

## Verification
- Product listings: Unaffected (use same flow)
- Service listings: Now properly handles orders with missing pricing fields

## Deployment Required
Deploy the updated edge function:
```bash
supabase functions deploy create_payment_intent
```

# Block User Functionality Fix

## Issues Reported
1. When reporting a post and clicking "block user" toggle, the user was not actually blocked
2. Blocked users' posts still visible in feed
3. Messages still received from blocked users

## Root Causes Found
1. **ChatScreen.tsx missing `onBlockUser` prop**: The ReportUserModal in ChatScreen was not receiving the `onBlockUser` callback, so the toggle did nothing
2. **No blocked user filtering in messaging**: `getConversations()` didn't filter out blocked users
3. **No blocked user filtering in listings**: React Native listing service lacked blocked user filtering (iOS had it)
4. **Real-time messages not filtered**: Subscribed messages from blocked users still came through

## Fixes Applied

### 1. ChatScreen.tsx - Added Block Functionality
- Imported `blockUser` from userService
- Added `handleBlockUser` function with confirmation dialog
- Passed `onBlockUser={handleBlockUser}` to ReportUserModal

### 2. userService.ts - Added Helper Functions
- `getBlockedUserIds(userId)`: Returns all blocked user IDs (both directions)
- `hasBlockingRelationship(userId1, userId2)`: Checks if blocking exists between two users

### 3. messagingService.ts - Filtering Blocked Users
- `getConversations()`: Now filters out conversations with blocked users
- `sendMessage()`: Checks blocking relationship before sending
- `subscribeToMessages()`: Ignores real-time messages from blocked users

### 4. listingService.ts - Filtering Blocked User Listings
- `getListings()`: Filters out listings from blocked users
- `searchListings()`: Filters search results from blocked users
- `fallbackSearch()`: Filters fallback search results
- `getListingsByCategory()`: Filters category listings

## Files Modified
- `mobile/src/screens/messages/ChatScreen.tsx`
- `mobile/src/services/userService.ts`
- `mobile/src/services/messagingService.ts`
- `mobile/src/services/listingService.ts`

# Legal Documents Fix - "Failed to Load Document" Error

## Issue
All three legal documents (Terms of Service, Privacy Policy, Community Guidelines) displayed "Failed to load document" error when accessed in-app.

## Root Cause
The original implementation used `expo-asset` and `expo-file-system` to load HTML files from the `assets/legal/` folder. This approach can fail due to:
1. Asset bundling issues in React Native
2. File system access problems on different platforms
3. Metro bundler configuration issues with HTML files

## Solution
Replaced the file-based loading approach with **embedded HTML content** directly in the component as template strings. This is more reliable because:
- No file system operations required
- No asset bundling dependencies
- Works consistently across all platforms
- Instant content loading (no async operations)
- Theme-aware styling applied at render time

## Changes Made

### LegalDocumentScreen.tsx - Complete Rewrite
- Removed `expo-asset` and `expo-file-system` dependencies
- Removed loading/error states (content is always available)
- Added `generateHtml()` function that wraps content with themed CSS
- Added `TERMS_CONTENT`, `PRIVACY_CONTENT`, and `COMMUNITY_CONTENT` as template strings
- Content is comprehensive and matches source documents from `legaldocs/` folder

### Content Included
1. **Terms of Service**: Full legal terms including acceptance, service rules, DMCA, warranty disclaimers, limitation of liability, indemnity, and contact info
2. **Privacy Policy**: Data collection, usage, sharing, retention, security measures, user rights, and contact info  
3. **Community Guidelines**: Core rules, prohibited content, content standards (hate speech, harassment, threats, etc.), marketplace-specific rules, and violation consequences

## Files Modified
- `mobile/src/screens/legal/LegalDocumentScreen.tsx` (complete rewrite)

# Purchase Confirmation Modal - Service vs Product Flow Differentiation

## Issue
After purchasing a service listing, the "What Happens Next" section on the receipt displayed the same steps as for products (delivery, photo upload, confirm receipt), instead of describing the PIN confirmation process used for services.

## Solution
Updated `PurchaseConfirmationModal.tsx` to check `listing.listing_type` and display different flows:

### For Services (`listing_type === 'service'`):
1. **Schedule the Service** - Contact seller to arrange time/place
2. **Service Completion** - Seller completes the service
3. **Share Your PIN** - Give 4-digit confirmation PIN to seller after satisfaction
4. **Payment Released** - Seller enters PIN to complete transaction

Includes a bold warning notice:
> **Important for Sellers**
> **We cannot guarantee payment unless the PIN is received.** The seller must obtain your confirmation PIN to complete the transaction and receive payment.

### For Products (`listing_type === 'product'`):
Original flow retained:
1. Seller Prepares Item
2. Delivery & Photo Upload
3. You'll Be Notified
4. Confirm Receipt

### Escrow Timeline Section
Also updated to show appropriate timeline:
- **Services**: Order Processing → Service Completion → PIN Confirmation
- **Products**: Order Processing → Delivery → Confirm Receipt

## Files Modified
- `mobile/src/components/PurchaseConfirmationModal.tsx`

# Chat Screen Navigation Fix - Back Button Stuck Issue

## Issue
When users accessed a DM via "Contact Seller/Buyer" from a listing, they would get stuck in that conversation:
1. Click "Contact Seller" from listing → opens Chat
2. Click back arrow → goes back to listing instead of messages list
3. Click Messages tab → shows the same DM
4. Click back arrow → goes back to home/listing instead of ConversationsList

Users could not access the full messages list after contacting someone from a listing.

## Root Cause
When navigating to Chat via `navigation.navigate('Messages', { screen: 'Chat', ... })`, the Chat screen becomes the only screen in the Messages stack. The `goBack()` function navigates to the previous screen in the overall navigation history (the listing), not to ConversationsList, because ConversationsList was never in the stack.

## Fixes Applied

### 1. ChatScreen.tsx - Updated Back Button Logic
Changed the back button handler to explicitly navigate to ConversationsList by default:
- If `returnScreen === 'ListingDetail'` → navigate back to the listing
- If `returnScreen === 'OrderDetail'` → navigate back to the order
- **Default**: Navigate to `Messages > ConversationsList` instead of calling `goBack()`

This ensures users can always access the full messages list after viewing a chat.

### 2. TabNavigator.tsx - Added Messages Tab Listener
Added a `tabPress` listener to the Messages tab (similar to existing Wallet tab logic):
- Intercepts tab press
- Always navigates to `ConversationsList`
- Prevents getting stuck on Chat screen when tapping Messages tab

## Files Modified
- `mobile/src/screens/messages/ChatScreen.tsx` - Updated back button navigation
- `mobile/src/navigation/TabNavigator.tsx` - Added Messages tab listener
