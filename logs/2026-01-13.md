# 2026-01-13 - Duplicate Order Prevention & Listing Archival Fix

## Issues Fixed

### 1. Duplicate Orders When Cancelling Payment
**Problem**: Clicking "Buy Now", cancelling the payment sheet, then clicking "Buy Now" again would create duplicate orders for the same listing.

**Root Cause**: `createOrder()` had no check for existing active orders for the same listing + buyer combination.

**Fix**: Added duplicate prevention check in `createOrder()` that throws an error if buyer already has an active order for the listing.

### 2. Listing Not Archived When Order Created
**Problem**: Listings were only archived when seller accepted the order, not when the order was placed. This allowed other buyers to also purchase the same item.

**Fix**: 
- Moved archive logic from `acceptOrder()` to `createOrder()` - listing is now archived immediately when an order is created
- Updated `deletePendingOrder()` to unarchive the listing when a pending order is cleaned up
- Updated `cancelOrder()` to only unarchive if no other active orders exist for the listing

## Files Changed

### `mobile/src/services/orderService.ts`
1. **`createOrder()`**: 
   - Added duplicate order check before creating new order
   - Added listing archival after order creation
   
2. **`acceptOrder()`**: 
   - Removed redundant archive logic (now handled at creation)

3. **`deletePendingOrder()`**: 
   - Now includes `listing_id` in order fetch
   - Unarchives listing after deleting pending order (only if no other active orders exist)

4. **`cancelOrder()`**: 
   - Updated to only unarchive listing if no other active orders exist for that listing

### New Edge Function: `supabase/functions/cleanup-stale-pending-orders/index.ts`
Safely cleans up abandoned pending orders:
- Only targets orders with `payment_status: 'pending'` (never authorized)
- Only targets orders older than 30 minutes
- Verifies no Stripe payment was processed before deletion
- Unarchives listings only if no other active orders exist
- Multiple safety checks to prevent data loss

## Safety Measures in Cleanup Function
1. Only deletes `payment_status: 'pending'` + `order_status: 'placed'` orders
2. 30-minute threshold ensures users have time to complete payment
3. Verifies Stripe PaymentIntent status before deletion
4. Skips orders where payment was actually processed
5. Double-checks order state before deletion
6. Uses conditional delete with extra WHERE clauses

## 3. Service Fee Display Issue on Order Details

**Problem**: On the Order Details screen, the service fee was showing as $0.00 even though the total price was correctly calculated (e.g., Subtotal: $0.50, Service Fee: $0.00, Total: $0.81 - should show Service Fee: $0.31).

**Root Cause**: 
- `marketplace_fee_cents` field was hardcoded to 0 when creating orders in `orderService.ts`
- OrderDetailScreen was displaying `marketplace_fee_cents` directly instead of calculating it from the price difference

**Fix**:
1. **OrderDetailScreen.tsx**: Calculate service fee dynamically as `buyer_price_cents - seller_price_cents` instead of using `marketplace_fee_cents`
2. **orderService.ts**: Calculate and store the correct `marketplace_fee_cents` value when creating orders
3. Also updated Subtotal to use `seller_price_cents` instead of `price_cents` for consistency

**Changes**:
- `mobile/src/screens/orders/OrderDetailScreen.tsx`: Updated Order Summary section to calculate fees properly
- `mobile/src/services/orderService.ts`: Added marketplace fee calculation in `createOrder()`

**Testing**:
- Verify service fee displays correctly on active order detail pages
- Verify subtotal shows seller's price
- Verify total shows buyer's price (including fees)

## 4. Wallet Tab Navigation Issue

**Problem**: When clicking the Wallet tab icon, users would sometimes land on the Orders page instead of the main Wallet page, making it difficult to access wallet features. This occurred because:
1. Clicking the active order banner navigates to Wallet → OrdersList
2. React Navigation preserves stack state, so clicking Wallet tab again would show OrdersList
3. Users couldn't easily get back to the main Wallet screen

**Root Cause**: React Navigation's default tab behavior preserves the navigation stack for each tab. When navigating to `OrdersList` via the active order banner, the Wallet stack would remember this screen as the last visited, showing it instead of `WalletMain` when the tab was pressed.

**Fix**: Added a `tabPress` listener to the Wallet tab in `TabNavigator.tsx` that always navigates to `WalletMain` when the tab is pressed, regardless of the current navigation state.

**Changes**:
- `mobile/src/navigation/TabNavigator.tsx`: Added tab press listener that resets to WalletMain

**Testing**:
- Click active order banner from Home → should navigate to Orders page
- Click Wallet tab icon → should navigate to main Wallet page
- Verify Orders page back button still works correctly
- Verify normal navigation within Wallet stack (e.g., PayoutHistory) works properly
