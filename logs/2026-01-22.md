## Root Cause
The `notify_new_message()` trigger function had insufficient error handling:
1. No validation that the conversation exists before trying to look up participants
2. Silent failures when `send_onesignal_notification()` encountered errors
3. No logging to help diagnose issues

## Fix Applied

### Updated Trigger Function
**File:** `docs/sql/onesignal_notification_triggers.sql`

Improved the `notify_new_message()` function with:
1. **Conversation existence check** - Validates conversation exists before processing
2. **Better recipient validation** - Explicit NULL check with warning logging
3. **Error handling** - Wraps notification send in try/catch to prevent silent failures
4. **Warning logs** - Adds RAISE WARNING statements for debugging

### Diagnostic Script Created
**File:** `docs/sql/fix_message_notification_trigger.sql`

Created a comprehensive diagnostic and fix script that:
- Checks if trigger is enabled
- Provides improved trigger function with error handling
- Includes diagnostic queries to check recent messages and their notifications
- Helps identify if notifications are being created but not delivered

# 2026-01-22 - Offers Visibility Enhancement

## Summary
Added visible offer banners on Home screen to make sent/received offers easy to find, matching the Swift version's approach.

## Changes Made

### New Files Created
- `mobile/src/context/OfferMonitorContext.tsx` - Context provider that monitors pending offers
  - Tracks pending received offers (require action)
  - Tracks pending sent offers (awaiting response)
  - Real-time subscription to offer changes
  - Periodic refresh (5 minutes, matching iOS)

- `mobile/src/components/ActiveOfferBanner.tsx` - Banner component for pending offers
  - Purple/violet theme to distinguish from orders (red)
  - Shows count of received and sent offers
  - Pulsing indicator animation
  - Navigates to My Offers screen on tap

### Updated Files
- `mobile/src/components/index.ts` - Export new ActiveOfferBanner
- `mobile/src/context/index.ts` - Export new OfferMonitorProvider and hook
- `mobile/App.tsx` - Wrap app with OfferMonitorProvider
- `mobile/src/screens/home/HomeScreen.tsx` - Added offer banner below active order banner
- `mobile/src/screens/offers/OffersScreen.tsx` - Call refreshOfferMonitor on focus to keep banner in sync

## How It Works
1. `OfferMonitorContext` monitors the database for pending offers where the user is either:
   - The recipient (`offer_to_user_id`) - offers requiring their action
   - The sender (`offer_from_user_id`) - offers awaiting response
   
2. When offers exist, `ActiveOfferBanner` appears on Home screen:
   - Shows "Offer Received" / "Offers Received" for incoming
   - Shows "Offer Sent" / "Offers Sent" for outgoing
   - Shows combined message when both exist
   
3. Tapping the banner navigates to Profile → My Offers screen

## Architecture
Following the existing pattern from Swift:
- Swift: `AllMyOffersView` accessible from `ProfileTabView`
- Swift: `ActiveOrderMonitor` for orders (separate from offers)
- RN: `OffersScreen` accessible from Profile → My Offers
- RN: New `OfferMonitorContext` for offer visibility

The existing linter errors in HomeScreen (lines 191, 205) are pre-existing navigation type issues, not introduced by this change.

# 2026-01-22 (Update 3) - Fix Offers Query Ambiguous FK Error

## Problem
Error loading offers: `PGRST201 - Could not embed because more than one relationship was found for 'offers' and 'listings'`

## Root Cause
The `offers` table has 3 foreign keys to `listings`:
- `offers_listing_id_fkey` (listing_id)
- `offers_offer_listing_id_fkey` (offer_listing_id) - legacy
- `offers_seek_listing_id_fkey` (seek_listing_id) - legacy

When using `listing:listings(*)`, Supabase doesn't know which FK to use.

## Fix
Specify the explicit FK name: `listing:listings!offers_listing_id_fkey(*)`

## Files Fixed
- `mobile/src/context/OfferMonitorContext.tsx` - 2 queries
- `mobile/src/screens/offers/OffersScreen.tsx` - 2 queries
- `mobile/src/services/offerService.ts` - 3 queries

# 2026-01-22 (Update 2) - Payout Setup Status Sync Fix

## Problem
Users completing Stripe Connect onboarding were seeing "Complete Payout Setup" button even after Stripe confirmed their payout account was active. Tapping the button showed "Success - Your payout account is already set up!" but the UI didn't update.

## Root Cause
The `connect_onboarding` edge function was detecting when onboarding was complete but **not syncing the status to the database**. The `stripe_payouts_enabled` and `stripe_details_submitted` fields stayed `false` in the database, causing the wallet screen to show the wrong UI.

The system relied on Stripe webhooks (`account.updated` event) to sync this status, but webhooks can be delayed, misconfigured, or missed.

## Fixes Applied

### 1. Edge Function: `connect_onboarding` (both versions)
**Files:** 
- `supabase/functions/connect_onboarding/index.ts`
- `supabase_functions/connect_onboarding_fixed/index.ts`

When detecting onboarding is already complete, now updates the database:
```typescript
// IMPORTANT: Sync database with Stripe's actual status
const { error: syncError } = await supabaseAdmin
  .from("users")
  .update({
    stripe_payouts_enabled: true,
    stripe_details_submitted: true,
    updated_at: new Date().toISOString(),
  })
  .eq("id", userId);
```

### 2. WalletScreen (React Native)
**File:** `mobile/src/screens/wallet/WalletScreen.tsx`

When `onboarding_complete: true` is returned, immediately update local state:
```typescript
if (data?.onboarding_complete) {
  setHasStripeAccount(true);
  setStripeAccountEnabled(true);
  Alert.alert('Success', 'Your payout account is already set up!');
  loadWalletData(); // Refresh wallet data
}
```

## How Status Sync Now Works
1. **Primary:** `account.updated` webhook syncs status when Stripe fires the event
2. **Fallback:** Calling `connect_onboarding` syncs status if webhook was missed
3. **Client-side:** Immediate UI update when server confirms onboarding is complete

## Testing
After deploying the edge function:
1. User taps "Complete Payout Setup"
2. Server detects onboarding is already complete
3. Server syncs `stripe_payouts_enabled = true` to database
4. Client receives `onboarding_complete: true`
5. Client updates local state and refreshes
6. UI now shows "Request Payout" and "History" buttons

# 2026-01-22 (Update 4) - Delivery Confirmation Flow Fix

## Problem
1. Seller saw error "Cannot mark as delivered - order must be accepted first" 
2. Buyer was able to upload a delivery confirmation photo (should only be seller)
3. "Mark as Delivered" button shown in wrong order states

## Root Cause
Multiple UI/logic inconsistencies in the order delivery flow:

1. **React Native (OrderDetailScreen.tsx)**: Showed "Mark as Delivered" button when status was `seller_confirmed` OR `in_progress`. But `seller_confirmed` means already delivered!

2. **iOS (OrderDetailView.swift)**: `canMarkDelivered` allowed `placed` OR `inProgress` status. Sellers could try to mark delivered before accepting the order.

3. **iOS (MyTransactionsView.swift)**: "Mark Delivered" button shown for ALL seller orders regardless of status.

4. **iOS (OrderService.swift)**: Service layer allowed marking delivered from `placed` status, inconsistent with React Native which required `in_progress`.

## Fixes Applied

### 1. React Native - OrderDetailScreen.tsx
Changed button visibility from:
```typescript
if (order.status === 'seller_confirmed' || order.status === 'in_progress')
```
To:
```typescript
if (order.status === 'in_progress')
```

### 2. iOS - OrderDetailView.swift
Changed `canMarkDelivered`:
```swift
// Before: isSeller && (currentOrder.orderStatus == .placed || currentOrder.orderStatus == .inProgress)
// After: isSeller && currentOrder.orderStatus == .inProgress
```

Also fixed PIN entry for services to require `in_progress` only.

### 3. iOS - MyTransactionsView.swift
Added status check for "Mark Delivered" button:
```swift
// Before: if !isBuyer
// After: if !isBuyer && order.orderStatus == .inProgress
```

### 4. iOS - OrderService.swift
Made service layer consistent:
```swift
// Before: guard [.placed, .inProgress].contains(order.orderStatus)
// After: guard order.orderStatus == .inProgress
```
Error message now matches RN: "Cannot mark as delivered - order must be accepted first"

## Correct Order Flow (After Fix)
1. **Placed**: Buyer created order, seller needs to Accept
2. **In Progress**: Seller accepted, can now Mark as Delivered (with photo)
3. **Seller Confirmed**: Seller marked delivered, buyer needs to Confirm Received
4. **Completed**: Buyer confirmed, funds released to seller
