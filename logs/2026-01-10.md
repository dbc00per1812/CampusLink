# CampusLink Development Log - January 10, 2026

## Campus Filter Fix (React Native)

### Issue
Campus filter was not working in the React Native version. Despite users signing up with proper email and selecting the proper campus, listings from all campuses were being shown.

### Root Cause
In `mobile/src/services/listingService.ts`, the Supabase PostgREST filter was using an **alias** (`user.campus`) instead of the **table name** (`users.campus`) when filtering on the related users table.

**Before (incorrect):**
```javascript
query = query.eq('user.campus', currentUserCampus);
```

**After (correct):**
```javascript
query = query.eq('users.campus', currentUserCampus);
```

### Technical Explanation
When using Supabase's nested select with inner join:
```javascript
.select('*, user:users!inner(*)')
```

- `user:` is an **alias** for the response object structure
- `users` is the **table name** used by PostgREST for filtering
- PostgREST filters require the actual table name, not the alias

### Files Changed
- `mobile/src/services/listingService.ts` (line 100)

### Affected Screens
- HomeScreen - uses `getListings({ filterByCampus: true })`
- CategoryBrowseScreen - uses `getListings({ filterByCampus: true })`

### Status
✅ Fixed - Campus filter now correctly uses `users.campus` for PostgREST filtering

## DM Send Message RLS Error Fix (New Users)

### Issue
New users were getting error `42501: "new row violates row-level security policy for table 'messages'"` when trying to send DMs to sellers.

### Root Cause
The RLS (Row Level Security) policy on the `messages` table in Supabase was too restrictive or misconfigured, preventing new users from inserting messages even when they were legitimate conversation participants.

### Solution

#### 1. Created SQL Fix Script
- **File**: `docs/sql/fix_messages_rls.sql`
- Provides SQL to drop and recreate correct RLS policies for:
  - `messages` table (SELECT, INSERT, UPDATE, DELETE)
  - `conversations` table (SELECT, INSERT)
  - `users` table (SELECT, INSERT, UPDATE)
- Correct INSERT policy for messages only requires:
  - `sender_id = auth.uid()` (user is the sender)
  - User is a participant in the conversation (buyer or seller)
- Does NOT require extra EXISTS check for `public.users` (FK constraint handles that)

#### 2. Enhanced Error Handling
- **File**: `mobile/src/services/messagingService.ts`
- Added verification that user is a participant in the conversation before sending
- Added detailed console logging for debugging
- Improved error message for RLS violations (code 42501)
- Suggests signing out and back in as a workaround

### Files Changed
- `docs/sql/fix_messages_rls.sql` (new)
- `mobile/src/services/messagingService.ts`

### Steps to Fix
1. Go to Supabase Dashboard > SQL Editor
2. Run the SQL from `docs/sql/fix_messages_rls.sql`
3. Test with a new user account

### Status
✅ SQL Fix Ready - Run in Supabase to apply

## Campus Filter Race Condition Fix

### Issue
Campus filter was inconsistent for new users - sometimes working, sometimes not. The campus icon wasn't showing on the home screen, and IU accounts were seeing Purdue posts.

### Root Cause
Race condition where:
1. HomeScreen loads before user profile is fully created in database
2. Campus query returns null/error because profile doesn't exist yet
3. Listings load without campus filter applied

### Changes Made

#### 1. Added Retry Logic to Campus Loading
- **HomeScreen.tsx**: `loadUserCampus()` now retries 3 times with 1s delay
- **listingService.ts**: `getCurrentUserCampus()` now retries 3 times with 500ms delay  
- **forumService.ts**: `getCurrentUserCampus()` now retries 3 times with 500ms delay

#### 2. Added Campus Change Detection
- **HomeScreen.tsx**: Added `useEffect` to reload listings when `userCampus` state changes
- Ensures listings are re-filtered if campus loads after initial render

#### 3. Added Debug Logging
- **authService.ts**: Logs campus value being saved and verifies it was saved correctly
- **HomeScreen.tsx**: Logs campus loading and initialization flow

### Files Changed
